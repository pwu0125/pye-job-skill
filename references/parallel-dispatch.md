# 并行派发作战模式（阶段五子代理编排）

主卡进入阶段五并行派发前必读。九条规则：

1. **波次划分以「父代验收通过」为准，不以「子代理回报完成」为准**——下一波只能含依赖全部通过父代实测验收的任务；子代理的自述是 claim，父代亲自跑验证命令才是 evidence。
2. **同波派发前查文件面 AND 资源面都不相交**——两张卡触碰同一文件或同一目录则串行；文件面不相交（如 llm/ vs data/trees/ vs data/benchmark/）还不够：两张卡若抢同一限流 API（如 Tushare 每小时限额）、同一端口、同一外部服务，同样串行。任务卡 Background 必须申报本卡占用的外部资源（API/端口/服务名），派发前对照申报表查冲突——文件不重叠但抢同一限流通道，是最常见的隐性并行失败。
3. **父代验收协议 = 重跑关键验证 + 专项扫描**——至少重跑该卡的验证命令（pytest/--check）核对输出与自述一致；凭据相关任务（LLM client/key 处理）另跑泄漏扫描（grep 密钥样式串）。扫描命中先看是否为脱敏函数的单测假串——redaction 测试故意含假凭据样式，那是用例不是泄漏；真实 key 零命中才放行。
4. **提交按验收节奏分批**——同波多个任务验收通过后合批提交，不逐任务碎提交；未验收的产出不进 commit。验收提交前扫一遍 git status，把先前已验收任务遗留的未跟踪文件一并收编进这批（验收点是让工作区归零的时机，散落的未跟踪文件下次会被误认成新任务的产物）；样例交付物落在 gitignore 目录（如 reports/）时按需 `git add -f` 显式入库——被忽略的交付物等于没交付。
5. **回报即验收即派下一波**——每个子代理回报送达后立即验收，验收通过马上派发该任务解锁的下一波，不让空闲窗口等齐全部回报。
6. **基础设施性失败与任务性失败分流**——子代理死于上游限流（HTTP 429）或网络断连，不是任务的错：先查磁盘残留（半成品文件/测试），残留保留并在重派卡里注明位置与完成度，允许续写或重写；重派卡带回原卡全部三要素，只追加续作说明，并从死会话的 live transcript 尾部抢救侦察结论（锚点位置、参数文件路径、复现方法）写进重派卡背景——前任已付成本的侦察不带回来，重派就要重付一遍。任务性失败（跑偏/验证不过/回报无证据）才走改卡→修订号+1→重派。
7. **子代理纠错回流卡源**——子代理报告卡片本身的事实错误（如参照实例张冠李戴）时：先亲自验证其证据，成立则修正 task.md 源并修订号+1，产出物里要求留 provenance；不许只改产出不改卡——卡链是唯一事实源，下游还会按卡派发。
8. **Interface Contract 即并行许可**——plan.md 已锁定 Interface Contracts 时，下游任务可按契约 schema 先行开发，不等上游实现落地：输入按契约消费、上游产物缺失时渲染「待接入」占位不阻塞、上游落地后补联调烟测。**契约带版本号 vN，任务卡记录消费版本；契约变更（vN→vN+1）时，所有消费旧版本的卡自动进「待复核」清单——「待接入」占位不许掩盖集成欠账。**依赖链里只有「契约未定」才是硬阻塞，「实现未到」不是——把可并行的下游扣在手里串行等，是白送工期。
9. **进度查询走委派考古**——用户中途问进度或回报缺位时：delegate_task 的 list 只列活体会话，已死/已完成的要靠 live/ 目录考古——读 `~/.hermes/cache/delegation/live/<id>/manifest.json` 的 goal 定位是哪张卡，tail 对应 task-N.log 的 final 行看真实终态（completed/failed+错误原文）。三源对账（活体列表、log 终态、仓内 commit 链）后再报进度，禁把「没收到回报」说成「还在跑」——死会话往往就是关键路径停摆的唯一证据。
